# Task 4 — Ролевая модель доступа к Kubernetes (RBAC)

Роли разграничены по двум осям: **уровень доступа** (просмотр / управление / привилегированный) × **область** (namespace / весь кластер). Имя роли описывает её права; кто ей пользуется — в колонке «Группы». Разграничение опирается на оргструктуру PropDevelopment: у каждой продуктовой команды свой DevOps и свой namespace, платформенные и надзорные функции — на уровне кластера, безопасность (секреты, управление правами) — у ИБ-специалиста.

| | Только просмотр | Управление |
|---|---|---|
| **Свой namespace** | namespace-viewer (разработчики) | namespace-devops (DevOps команд) |
| **Весь кластер** | cluster-viewer (аудиторы, архитекторы, поддержка) | cluster-devops (платформенный DevOps) |

Над сеткой — привилегированная роль ИБ (секреты + управление RBAC).

---

| Роль | Права роли | Группы пользователей |
| --- | --- | --- |
| **namespace-viewer** (Role) | Только чтение в пределах своего namespace: `get, list, watch` на `pods`, `pods/log`, `deployments`, `services`, `configmaps`. Без доступа к `secrets`, без записи. | Разработчики продуктовых команд |
| **namespace-devops** (Role) | Управление сервисами в пределах своего namespace: `get, list, watch, create, update, patch, delete` на `pods`, `deployments`, `services`, `configmaps`, `networkpolicies`, `ingresses`, `httproutes`. Без доступа к `secrets` (управляются ИБ) и без управления RBAC-объектами. | DevOps-инженеры продуктовых команд |
| **cluster-viewer** (ClusterRole) | Только чтение по всему кластеру: `get, list, watch` на обычные ресурсы во всех namespace. Без доступа к `secrets`, без записи. | Аудиторы, архитекторы, сотрудники поддержки |
| **cluster-devops** (ClusterRole) | Управление инфраструктурой всего кластера: `get, list, watch, create, update, patch, delete` на обычные ресурсы во всех namespace + кластерные ресурсы (`nodes`, `persistentvolumes`). Без доступа к `secrets` и без управления RBAC-объектами. | Платформенные DevOps-инженеры |
| **security-admin** (ClusterRole) | Привилегированная роль. Доступ к `secrets` по всему кластеру (`get, list, watch` и управление) + управление RBAC-объектами (`roles`, `rolebindings`, `clusterroles`, `clusterrolebindings`). | Специалист по ИБ |

---

**Пометка про хранение секретов.** В целевой архитектуре секреты выносятся за контур кластера в внешнее хранилище (HashiCorp Vault): доступ раздаётся политиками Vault, ИБ управляет централизованно, секреты не хранятся в etcd кластера. Это закрывает находку из анализа (хранение ключей/секретов не описано, k8s Secret по умолчанию не шифрует, а только кодирует). Для данного задания секреты оставлены как k8s `Secret` под управлением привилегированной роли ИБ — чтобы продемонстрировать разграничение доступа к секретам средствами RBAC (как требует задание: просмотр секретов = привилегированное действие).

**Принципы, заложенные в модель:**
- **Least Privilege** — каждая группа получает минимум прав под свои задачи.
- **Тенант-изоляция по namespace** — продуктовые команды работают только в своих namespace (симметрично тенант-изоляции по УК из Task 3).
- **Separation of Duties** — разработка/эксплуатация (DevOps) отделены от управления секретами и правами доступа (ИБ); тот, кто деплоит, не раздаёт себе права.
