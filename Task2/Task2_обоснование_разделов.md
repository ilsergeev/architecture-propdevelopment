# Проверочный лист безопасности для бизнес-систем PropDevelopment

## Выбор разделов

Шаблон чек-листа взят из курса. Разделы приоритизированы под конкретные боли PropDevelopment и находки из Task 1 - что для компании критично, а что второстепенно.

Боли компании:
- Нет контроля данных: клиента можно зарегистрировать в нескольких точках без координации между ними, а внутренние потоки данных ограничены только бизнес-правилами, не системами.
- Партнёрские API без единых политик: партнёр из одной УК может видеть и менять данные клиентов и ЖК другой УК.

Инфраструктура: гибрид (свой ЦОД + приватное облако + аренда), бизнес-сервисы в Kubernetes.

---

### II. Безопасность данных - высокий

Самый больной раздел для компании: бьёт по первой боли и по 152-ФЗ. Данные, включая ПДн, хранятся в сыром виде (зашифровано или нет - по схеме непонятно), хранилища не разделены по классификации, ПДн стекаются в аналитическое хранилище без обезличивания. Бэкапы на схеме не указаны вовсе. Потоки данных не ограничены ничем, кроме бизнес-правил. Раздел проверяет ровно эти пробелы: классификацию, шифрование, управление ключами, резервное копирование, обезличивание и контроль целостности.

### I. Управление доступом - высокий

Бьёт по второй боли и по избыточному доступу. Не все внешние подключения проходят через firewall, и непонятно, как настроены права доступа к данным, - это открывает возможность управления чужими данными (на примере API ЖКУ). Не для всех внутренних ролей указаны системы авторизации (например, аналитик BI). Замкнутый контур для чувствительных данных есть только у бухгалтерии - его можно взять за эталон. А из-за нескольких точек регистрации и продублированных на схеме auth-db-1/AD единого реестра учёток у компании фактически нет. Раздел проверяет MFA, минимальные привилегии, единый реестр, отзыв прав, замкнутые контуры и централизованный контроль.

### IV. Управление инцидентами - высокий

Компания достаточно крупная, чтобы SIEM был оправдан (для мелкой он был бы избыточен). Чтобы пройти аудит, нужны журналы инцидентов и система оповещений - это прямое пожелание. А с учётом недавней атаки на конкурентов вероятность инцидента для компании уже не нулевая. При этом без мониторинга бесконтрольные потоки данных означают, что утечку попросту не заметят. Раздел проверяет SIEM, оповещения, план реагирования, учения, статистику и регулярность аудитов.

### III. Защита инфраструктуры - средний

Раздел частью отвечает на опасения компании после атаки на конкурентов. Из плюсов: клиенты и собственники ходят через firewall. Но за трафиком внешних подрядчиков слежения нет, а туда, судя по описанию, могут просачиваться ПДн - то есть фильтрация трафика настроена не должным образом, а сегментации при работе с критическими данными не видно. Остальное в разделе (DDoS, IDS/IPS, антивирус, EDR, сканирование уязвимостей) - базовая гигиена, не про конкретные боли. Поэтому включаю с акцентом на периметр, сегментацию и партнёрский трафик.

### V. Специфические аспекты - низкий

Применимо к инфраструктуре, но в фокус проблем не попадает. Физбезопасность серверных актуальна (свой ЦОД есть), но это базовая гигиена. Облачная часть тоже применима, однако её ключевое - бэкапы и шифрование - уже учтено в разделе II, дважды не считаю. Мобильные устройства - вообще периферия. Логика простая: если у компании нормально с управлением доступом и безопасностью данных, то где физически лежат данные - уже не так значительно.

## Итог

| Раздел | Приоритет | Почему |
|---|---|---|
| II. Безопасность данных | Высокий | Первая боль: сырые ПДн, 152-ФЗ, потоки без контроля |
| I. Управление доступом | Высокий | Вторая боль + избыточный доступ + нет единого реестра |
| IV. Управление инцидентами | Высокий | Аудит, реакция на инциденты, слепота к утечкам |
| III. Защита инфраструктуры | Средний | Вторая боль частично; остальное - гигиена |
| V. Специфические аспекты | Низкий | Применимо, но не в фокусе |

В заполненном листе для каждого вопроса стоит «Да / Нет / Частично», где это видно из схемы и описания, и «Не определено», где данных недостаточно - такие вопросы выносятся на живую проверку при аудите.
